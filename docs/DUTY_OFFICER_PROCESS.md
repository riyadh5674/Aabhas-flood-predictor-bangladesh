# Aabhas Flood Predictor — Duty Officer Process

## 1. Purpose

Define the human-in-the-loop process for reviewing and approving flood alerts generated by the Aabhas system before dispatch to external channels. This process ensures accountability, prevents alert fatigue, and maintains the "research prototype — not an official warning" designation.

|------|----------------|---------|
| **Duty Officer** | Review draft alerts, approve/reject, escalate | Rotating roster |
| **Technical Lead** | System health, threshold tuning, incident response | |
| **FFWC Liaison** | Coordinate with official warnings, resolve conflicts | |

## 4. Approval Rules

| Alert Level | Auto-Approve | Requires Officer | Escalation Timeout |
|-------------|--------------|------------------|-------------------|
| **Watch**   | Configurable (default: NO) | Yes (if not auto) | 30 min |
| **Warning** | NO | Yes | 15 min |
| **High**    | NO | Yes | 5 min |

- **Auto-approve watch:** Can be enabled in `alert_config.json` for low-risk periods
- **Escalation:** If not acted on within timeout, escalate to next officer on roster
- **Rejection:** Officer can reject with reason; alert logged but not dispatched

## 5. Duty Officer Workflow

### 5.1 Receiving Notification
1. System creates draft alert → writes to `system/data/processed/alerts_draft/`
2. Notification sent to duty officer (email/webhook/dashboard)
3. Dashboard shows pending count at `/alerts?status=draft`

### 5.2 Review Checklist
For each draft alert, verify:
- [ ] **Station & location** valid (cross-check with FFWC station list)
- [ ] **Probability** plausible given current conditions
- [ ] **Risk band** matches probability per thresholds
- [ ] **No conflicting FFWC advisory** for same station/horizon
- [ ] **Recent alerts** for same station (check cooldown/escalation)
- [ ] **Monsoon context** appropriate (season, upstream conditions)

### 5.3 Decision Actions
| Action | Effect |
|--------|--------|
| **Approve** | Move to `alerts_approved/`, dispatch via enabled channels |
| **Reject** | Mark rejected, log reason, no dispatch |
| **Escalate** | Forward to senior officer with context |
| **Defer** | Keep as draft, re-review in 1 hour (max 2 deferrals) |

### 5.4 Approval via API
```bash
# Approve
curl -X POST "https://api.example.com/alerts/{draft_id}/approve" \
  -H "X-Admin-API-Key: $ADMIN_KEY" \
  -d "approver=officer_name"

# List pending
curl "https://api.example.com/alerts?status=draft" \
  -H "X-Admin-API-Key: $ADMIN_KEY"
```

## 7. Incident Response

### 7.1 Alert Storm (>20 alerts/hour)
1. Duty officer declares "alert storm"
2. Auto-approve watch alerts temporarily enabled
2. Technical lead investigates model/data issue
3. Communicate to stakeholders: "Elevated alert volume under review"

### 7.2 System Degradation
- If `/health` shows `degraded=true` or sources stale:
  - Duty officer notified immediately
  - Technical lead paged
  - Fallback: manual FFWC advisory monitoring

### 7.3 False Alarm Investigation
1. Officer marks alert as "false positive" in audit log
2. Technical lead runs post-event analysis within 48h
3. Threshold adjustment proposed if pattern detected

## 8. Audit and Compliance

All actions recorded in immutable audit log (`system/logs/alert_audit.jsonl`):
- Alert generation (model output)
- Draft creation
- Officer review (timestamp, officer ID, decision)
- Approval/rejection with reason
- Dispatch results per channel
- Escalation events

**Retention:** 3 years minimum (per disaster management regulations)

## 9. Training Requirements

All duty officers must complete:

- [ ] Alert evaluation workshop (4 hours, with historical cases)
- [ ] FFWC coordination protocol (1 hour)
- [ ] Quarterly refresher drills
